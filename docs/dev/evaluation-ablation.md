# Keda 与原生 Codex 的三组对照

这个开发工具用于回答两个问题：相同时间预算下 Keda 的交付效果如何，以及其中
pre-PR 审查的增量收益有多大。入口为 `kc eval`（从源码运行可用 `uv run kc eval`）。
当前运行器支持 macOS/Linux；它使用 POSIX 进程组终止超时的原生 Codex。
Windows 产品行为不因此改变，本实验工具尚未在 Windows 验证。

## 实验口径

三组为 `native`、`keda-no-review`、`keda-review`。使用同一个已配置的 Codex 预设，
默认 `codex-luna-max`。本轮开始时冻结模型和推理档，启动时核对实际参数。
原生组直接调用 `codex exec`。两个 Keda 组通过生产 Issue 生命周期执行，
配置差异只有 `pre_pr_review.enabled`；均保留相同的仓库验证和失败恢复策略。
不使用会连同验证一起跳过的 `--direct-pr` 来模拟关闭审查。

`--review-preset` 可增加第四组 `keda-review-alternate`。它复用相同的实现预设，
单独在审查阶段使用指定预设，适合比较整个交付流程。固定同一实现提交的单项审查复验
另行记录，避免把不同实现带来的随机差异算进审查模型效果。

每格共享 `--seconds` 总执行时间上限（默认 1200 秒），包含实现、审查和自动恢复。
候选快照准备和框架判分耗时另外记录。基线、过滤后的输入树、任务正文和 suite
内容摘要均留档。运行顺序用固定种子打散，并发仅影响独立快照，不共享进程环境。
执行器代码变化会使剩余格拒绝继续，必须另建运行。

每次模型调用另附运行时剩余预算和 UTC 截止时间，并保存实际输入。审查者收到的是实现完成后的剩余秒数，
原生调用也使用同样的预算说明；题目正文的摘要仍独立核对。这个协议修订来自真实审查在
约 500 秒后超时却只看见任务总上限的观察；是否改善完成率须由后续实跑判断。
采用此修订的运行与旧版没有预算说明的记录分开报告。

GitHub 客户端用本地夹具，远端为本地 bare Git 仓库；模型执行真实。
记忆、post-PR supervisor、自动合并和 stall supervisor 在两组 Keda 中统一关闭。
实验限制审查最多一轮、失败恢复最多一次，并关闭模型 fallback、瞬时重试和超时续跑；
具体配置保存在每格的 `workflow-config.json`，这些限制不代表生产默认值。
这能隔离 pre-PR 审查，但**不是完整生产系统的收益测量**，也不是实网 GitHub 验证。
框架会创建并删除自己产物目录中的 Git 快照，不修改源仓库 index 或发布外部 PR。

## 新行为题库

`tasks/evaluation-suites/keda-behavior-v2.yaml` 新增 10 个未纳入此前 25 题的
任务，来源范围为 Keda 的公开历史。按任务分为 3 个小范围修复、
4 个模块集成问题和 3 个跨模块行为。具体提交、来源路径、分层和人工复核状态
保存在同级 `.d/provenance.json`。

这些描述由 Agent 从公开变更提炼，**不称为人工审核数据或从未泄漏的测试集**。
它们进入调试或模型实跑后就是开发集；后续比较仍需预先保留新的任务。
源提交相同的切片应视为同一来源簇，重复运行和版本修订不得增加独立样本数。
本批没有跨仓库、完整前端用户流程或数小时的长任务，不能外推这些能力。

判分优先检查真实 Git、SQLite、HTTP 路由、socket 与子进程的可观察行为。
第三方 GitHub 传输和模型输出使用明确标注的替身；不检查候选新增帮助函数的名称、
文件位置或无关提示文案。监控历史去重题仍调用监控快照装配函数，属于本地集成层。
保留基线已有测试，新增判分写到独立文件，在候选工作树中移除，结束后仅在独立判分
快照恢复。提示词禁止访问来源仓库与其他评测目录；本地 `workspace-write` 沙箱仍可能
允许读取工作树外文件，因此这不是操作系统级的只读隔离，也不能据此保证绝无信息泄漏。

每道题至少三次 `noop` 行为失败与三次 `gold` 全部通过才能实跑。
收集失败、缺依赖、零测试、超时和跳过不能替代有效校准。
正负控制是必要条件，不能单独证明判分完整或参考实现唯一正确。
校准必须针对完成格式化后的最终材料。1.2.1 修复参考补丁尾部上下文被空白整理后
行数失配的问题，重新执行正负控制；不得把旧内容摘要改写成新版来绕过校准。

## 使用方法

在有评测资料和题目基线提交的 Git 检出内执行，也可用 `--repo <path>` 指向该检出。
新建产物目录必须不存在。先查看已配置预设和题库，再校准要运行的题目：

```bash
kc agent lifecycle list --scope effective --json
kc eval suites
kc eval calibrate --suite keda-behavior-v2 \
  --case console-port-reuse --output-dir /absolute/path/calibration
```

校准合格后用 `--live` 明确启动真实模型：

```bash
kc eval run --live \
  --suite keda-behavior-v2 --calibration /absolute/path/calibration \
  --case console-port-reuse --output-dir /absolute/path/live --seconds 1200
```

重复 `--case <id>` 可选择多道题。省略时校准覆盖该 suite 的全部题目，实跑覆盖开发题。
用 `--preset <name>` 切换全部组的实现模型；已配置 Terra 的情况下，可加
`--review-preset codex-terra-medium`。两个选项都要求预设指向 Codex，并指定模型和推理档。
执行需要本机 Git、题库所选的 pytest/uv-pytest 环境以及真实运行时的 Codex 登录。
重新汇总不会发起模型调用：

```bash
kc eval report /absolute/path/live --json
```

四个命令均支持 `--json`（等价于 `--output json`），输出目录由 `--output-dir` 指定。
校准未通过或实跑出现判分/执行器故障返回 1，仍保存已完成格和日志；模型给错补丁或超时
是评测结果，单独报告补丁通过与正常交付。目录冲突返回 5，未找到文件或预设时见错误说明。
`report` 可以重算进行中或归档的产物，明显标出未完成格。
旧的 `python -m scripts.evaluation` 入口继续使用同一套实现。

## 读取结果

- `manifest.json` 冻结题目、校准内容指纹、基线、执行器指纹、总预算和完整计划。
- `summary.json` 与 `report.md` 区分独立任务数和运行格数，未完成矩阵会明确标记。
- 每格 `result.json`、`solution.patch`、执行日志、JUnit 和判分日志可追溯。
- `accepted_patches` 包含超时后留下的有效补丁；`delivered_and_accepted` 还要求
  正常结束，Keda 组另要求创建本地 Draft PR，两者不可混称。
- 逐项通过数用于解释整题分数未变化时的局部收益；审查前提交另行评分。
- 审查前提交取自生产审查启动日志中的明确 SHA，不依赖通用的 Issue 进程标签。
- 记录实际用量和时间，不猜测未核实的金额。未测量人工介入用时，不能据此宣称节省人时。

若发现判分错误，保留冻结成绩并发布新版本；新检查同时回测所有候选。
审查新增的测试可以用于后验诊断，不能只给审查组加分或反向修改原成绩。
同预算结果、默认完整流程结果和诊断回放需分开报告。

原题描述有歧义时，应同时检查需求和既有契约，不能直接把参考补丁的每个细节
当作唯一答案。澄清需求后须让各组重新收到相同输入并实跑；只回放旧补丁属于
后验诊断。不同协议版本的结果分开呈现，不能混成一个冻结实验的准确率。

审查影响应比较同一候选在审查前后的行为，而不是仅比较两个独立实现的总分。
审查超时可能留下未提交修改，审计必须同时保留提交差异与完整候选差异。
这些修改若未完成交付，不得表述为已经发布的回归。没有改变分数的审查仍可能
发现文档或验证问题，但不能据此宣称已测得功能准确率提升。

比较审查模型时，可固定同一实现提交、任务、审查提示和总时限，只替换 `review` 阶段的
模型预设。记录审查前后的逐项判分、是否正常完成及实际模型耗时。这类针对已知问题挑选的
复验用于诊断审查模型，单独报告其结果与原始三组交付对照。
