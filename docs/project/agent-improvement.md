# Agent 评测方案与 Agent Teams

通过同一套 `kc` CLI 交付工程任务，先测清单 Agent 能否以可接受的成本稳定交付、少让人中途接手，再用同一套口径评估 Agent Teams。这样可以按任务类型判断哪些步骤值得交给多个角色协作。

## 单 Agent 评测（M13）

[黄金评测基线](https://github.com/ZataZhang/keda/blob/main/tasks/archive/P1-FEAT-20261019-140531-m13-golden-eval-baseline.md)已归档，待人工验收。它提供版本化题集、逐题冻结起点、隔离快照、隐藏判分、无模型校准和重复运行记录。运行方式见[评测与测试](../dev/evaluation.md)。

### 对照怎么跑

1. **冻结题集和起点。** 从可判分的历史任务中按难度和类型选题，保留开发集和留出集。候选运行在隔离快照中，结束后再注入隐藏测试。先用空改动和已知修复校准判分，记录题集版本和公开历史可能带来的泄漏限制。
2. **先比工作流，再调成本。** 用同一 Agent 预设、同一任务和相同时间上限，配对比较原生执行与 Keda 编排，每题两组先各跑三次。比较审查的增量收益时增加关闭发布前审查的一组。测试低成本预设、提示词或 skill 时，一轮只改变待评估的变量。Claude 对照的交付范围见[配对评测 PRD](https://github.com/ZataZhang/keda/blob/main/tasks/pending/P1-FEAT-20261019-180938-m13-keda-vs-claude-workflow-evaluation.md)。
3. **按统一标准验收。** 用预先冻结的行为检查和隐藏测试判定结果，单列已通过判分的补丁、正常完成的交付、超时和基础设施故障。评审模型补充可维护性等测试难以覆盖的维度，原始分数和分歧分别报告。评测报告保留逐题结果、配置、预算以及运行和判分证据。
4. **用真实任务补测接管。** 按任务类型和难度分组观察 GitHub Issue 到 PR 的真实交付，记录返工、人工修改和被迫接手的原因。离线对照用于验证质量、稳定性和可取得的用量，真实交付记录用于判断中途人工投入和一次通过合并情况。

### 看哪些指标

| 指标 | 记录口径 |
| --- | --- |
| **交付质量** | 合格交付数除以有效执行数，超时计入未交付，无法判分的基础设施故障单列。另报重复稳定性，真实任务再看一次通过合并率和返工次数。 |
| **单次合格交付成本** | 同批次所有尝试的已知总成本除以合格交付数，分子包含失败、重试、审查和修复。另报总耗时、各阶段用量和费用覆盖率。有费用缺失时标为部分记录，零合格交付时单列总耗用。 |
| **中途人工接管** | 统计人必须接手执行、补做修复或手动恢复的任务数，除以有完整记录的已启动任务数。另报记录覆盖率、主动处理时长和触发原因。任务授权、最终验收和等待时长另行记录。 |

先用基线确定任务类型的最低质量要求和可接受预算。一种方案达到质量要求后，再判断成本或接管是否有可重复的改善，同时报告其他指标的变化。最后用留出任务确认差异，按任务类型决定采用哪套配置。

## 下一步 · Agent Teams（数字员工）

先挑一类可明确切分、经常需要交接或独立复核的真实工程任务。由负责协调的 Agent 拆分目标并保留验收条件，执行 Agent 各自交付小范围改动，复核 Agent 汇总验证结果并指出未完成项。跨角色交接通过 `kc` 传递任务状态、产物和验证证据。任务授权和高风险决策由人负责。

用已验证的单 Agent 工作流作为对照，两组固定任务、验收标准和整项任务总预算。团队组把协调、交接、重复工作、复核和失败恢复一并计入成本与耗时。只有分工带来的交付质量或接管改善能在重复任务中覆盖额外成本时，才扩展到更多任务类型。

## 后续候选 · 受控的 skill 晋升（原 M14）

评测能稳定区分差异、样本充足且试点成本可接受时，再评估自动提出改进的增量收益。如果 M13 的报告已经足以指导人工调整，先保留这种方式。若要试点，优先验证 skill 草稿晋升一个场景。

1. 从本仓库的失败、审查、验证和人工修正中形成改进提案。
2. 用固定评测对照当前版本，确认收益或无退化，交给维护者逐条批准。
3. 记录提案、评测和产物版本，生效后监测并支持回到已验证的版本。

提案权限限于 skill、提示词、记忆或路由偏好。安全配置、凭据、验证门禁、自动合并授权、评测集、评审器与阈值由维护者独立管理。是否扩展到其他产物、批量批准或按任务路由，由试点的重复证据决定。
