## Why step 2 comes before step 3

Writing oracles at the end is the single largest time sink in this flow. New tests written under end-of-flow pressure fail for harness reasons — wrong response shape, missing fixture, collection markers, colliding test data — and each of those costs a debugging round that has nothing to do with whether the feature works. Written first, the same failures are cheap. A test that was red before the implementation and green after is also the most honest negative control available, and it costs no production code.

## Hard rule: never modify production code to make an oracle testable

Do not add fault-injection switches, failure modes, test-only config keys, counters, or observation hooks to `src/` or `frontend-*/` in order to make an oracle able to fail.

Allowed instead, in order of preference:

1. the red-before-implementation run from step 2;
2. mocking or patching at the test boundary (`monkeypatch`, fixture, dependency override);
3. a test-only subclass or fake that lives under `tests/`.

If none of those can make the oracle go red, record it in the evidence report as:

```
negative_control: not feasible — <one-line reason>
```

and move on. "Not feasible" is an accepted outcome. It is never a licence to reshape the product for its own test.

## Evidence collection conventions

- Pipe every verification command through `tee` into the evidence directory on its first run: `<command> 2>&1 | tee <EVIDENCE_DIR>/rv-N.log`. Raw logs are a by-product of running the command, not a separate task to be discovered later.
- Never screenshot a live one-time credential — invite links, reset links, tokens, session values. Close or collapse the reveal control first and capture the resulting status/state view instead. A screenshot proving "the invitation is pending" is worth the same as one showing the URL, and is safe to keep.

## Verification rounds

The verifier's findings are labelled `BLOCKER`, `SECURITY`, or `NON-BLOCKING`.

- Fix `BLOCKER` findings and resubmit. Fix `SECURITY` findings immediately, but they do not by themselves require a new verification round.
- `NON-BLOCKING` findings do not require a resubmission. Address them if cheap, otherwise leave them listed in the evidence report as known and accepted.
- There is a maximum of 2 verification rounds. If `BLOCKER` items still stand after round 2, stop. Do not start a third round. Append an `## Open Items For Human Review` section to the evidence report listing each unresolved `BLOCKER`, what you tried, and what decision is needed. Escalating an honest open item is the correct outcome; grinding a third round is not.
