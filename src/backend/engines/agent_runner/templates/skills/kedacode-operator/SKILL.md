# KedaCode Operator

Use this skill when the user asks to operate the KedaCode CLI or its managed runner. Match the request to one route in the table below, read that route's reference file (an absolute path once the skill is installed), then act. If the wording is a CLI direct translation rather than a phrase below, route by the command name. Default-model configuration snapshots (`model_config_snapshot`) are separate from executor reports; read the watch route for source and estimation semantics.

## Shared baselines (apply to every route)

- **Reference paths**: use `${CODEBUDDY_SKILL_DIR}` when available; otherwise resolve the absolute parent directory of the installed `SKILL.md` you actually read, then append `references/<file>.md`. Never resolve from the working directory or assume another Agent exposes this variable.
- **Confirmation means checking scope and existing authorization.** An explicit instruction already authorizing the target and side effects remains valid across routes and recovery; explain the action and continue without asking again. Ask only when required information or authorization is missing, the scope expands, or a new irreversible action needs approval. A read-only request never authorizes execution; replacing user-owned Skills still requires explicit replacement authorization.
- **Execution authorization delivers the closed loop, not a draft.** An imperative request to get work done — regardless of language: 「用 keda 做」「建个 issue」「发出去」; "use keda to do it", "create an issue", "push it out" — authorizes the whole route: the deliverable is the finished loop (Issue created, run started, PR published), with drafts shown inline as work proceeds. If a tool boundary seems to block the loop, verify it first (skill references, `kc schema --json`, `--help`) instead of stopping on an impression.
- **First-time bootstrap.** When the target repo's `AGENTS.md` lacks this collaboration convention, suggest adding it (execution authorization → closed loop) to the user once.

- **A read-only request gets a read-only command.** Never start `kc run` or `kc registry start` just because the user asked to *view* progress — an inspect, preview, or "just check" request never becomes execution. For execution, **`kc run` requires a target** (breaking change): pass `--issue <N>`, a PRD path (resolved via the PRD's `- GitHub Issue:` link — a PRD without one must first go through `kc issue create`), or `--all-ready` for the historical queue-draining behavior. Bare `kc run` fails with a usage error.
- **Batch aggregation is opt-in.** Follow the run-once reference for eligibility, the second pass after CI, and safe closeout. Verify the total PR exists before reporting delivery.
- **Unknown flag, default, or enum value**: read `kc schema --json` — read-only introspection derived from the live command tree: every command, flag, type, required flag, enum choices, default, and an example — instead of guessing from a table. Evidence packages that declare `stdout_assertions` must pass `kc evidence check` first; see run-once for its flags and exit codes. One caveat: `required` reflects the declaration layer only, so the persistent-write commands' `--scope` exports as `required=False` even though omitting it exits `2` — always pass `--scope` (and `--repo-id` for repository writes) on those.

## Consuming `kc` from a script or another Agent

Whenever the reader of the output is a program rather than a human, pass `--json` explicitly. `--json` is an alias of `--output json`; with neither flag the output stays the human table, **including when stdout is a pipe**, so never assume a machine format.

- Startup update checks never disturb a program: machine mode, the completion protocol, `--help`, `--version`, non-TTY stdin/stderr, and `KEDACODE_NO_UPDATE_CHECK=1` each skip the PyPI visit and the upgrade prompt entirely, so scripted invocations never block on a question.

- In JSON mode stdout carries data only. Progress, warnings, and errors go to stderr, so `command > out.json` cannot be polluted by log lines. For a foreground run this Agent starts and waits on, use `kc run ... --progress` and keep consuming stderr lines prefixed `KC_PROGRESS `; each prefixed line contains versioned JSON for lifecycle changes, a 30-second heartbeat, or the terminal `run.finished` result. Ordinary Agent output stays on stdout. Keep the process session open until `run.finished`; that event reports the runner command result, not PR merge or human acceptance.
- A failure in JSON mode writes one envelope to stderr: `{"error", "message", "suggestion", "retryable", "exit_code"}`. `suggestion` is a runnable command, and the only safe way to continue is `$?` — do not parse English.
- `kc ask` and `kc deliberate` reuse `--output` for an output **directory**, so `--output json` there means a directory literally named `json`. Neither takes `--json`; read their human summary or the written session files instead.
- Exit codes published by `kc --help` and by `kc schema --json` → `exit_codes.values`. The Name column is exactly the envelope's `error` value, so `$?` and stderr never disagree:

| Code | Name | Meaning | What the caller does |
|---|---|---|---|
| `0` | `ok` | Requested work completed (read-only output counts as success). | Continue. |
| `1` | `error` | Failure with no published category. | Read stderr, then retry or escalate. |
| `2` | `usage_error` | Flags or arguments do not form a valid command: bare `kc run`, mutually exclusive targets (e.g. `--from-prompt` with or without a PRD path), or a single-target-only flag used with `--all-ready`. | Fix the invocation; retrying unchanged fails again. |
| `3` | `not_found` | Target missing: repository, registry entry, agent, executable, or log. Also an explicitly targeted Issue that cannot be read or is closed, and the pre-run availability gate — a lifecycle stage (or its preset) resolves to an agent whose executable is not on this machine's `PATH`, refused before any Issue is claimed. | Switch target, or run the `suggestion`; for the gate, install that CLI or re-choose with `kc agent setup` / `kc agent setup --fix` — never by editing the fallback chain. |
| `4` | `permission_denied` | Not authorized: GitHub auth or a disabled repository. | Ask the human to authenticate or enable it; do not retry silently. |
| `5` | `conflict` | Current state blocks the request: `--all-ready` while a daemon polls the same queue, an explicitly targeted Issue that is live-claimed by another process or is `agent/blocked` with no unblock request, workflow template file already installed, loop entry already exists. | Rename, pass `--force` when the user asked for it, stop the competing process, or run the `suggestion` (for a live claim it names the holder host and PID; for a blocked Issue it is `kc blocked-continue --issue <N>`). |
| `10` | `dry_run_ok` | The plan is valid and nothing was written. Usable as a CI gate. | Treat as green only after checking the plan body. |

## Safety and compatibility

- **The terminal you are in may be `kc session`.** Bare `kc` in a TTY hands the terminal to the configured executor and returns that provider's exit code unchanged; KedaCode does not interpret the conversation, does not change permission policy, and does not start project services. A preview dev server starts only when the user explicitly asked for it (`kc preview start` / `status` / `stop`, loopback-only, KedaCode-owned process group), so never start one on speculation. See setup-and-config.
- **Stall supervision is on by default for eligible Issue runs.** Set `[agent_runner.stall_supervisor].enabled = false` to opt out. It is the only component that may terminate a live writing attempt, and it acts only after a closed-set `stalled` verdict plus a fresh scene/ownership recheck; absence of `[kc-stall-*]` lines can mean there was no eligible active run or supervision was explicitly disabled. See triage.
- Explain GitHub writes, Agent execution, and persistent background processes before carrying them out. A queue preview is read-only.
- **Hosted Runner**: before operating hosted credentials, maintenance or the optional Linux desktop, read `${CODEBUDDY_SKILL_DIR}/references/hosted-runner.md` (or resolve it beside the installed skill).
- **An explicit target does not need `agent/ready`**: readiness gates the daemon's *autonomous pick*, not a human-named run. Any open Issue can be run with `kc run --issue <N>` — including one made by hand with no PRD anchor and no labels. What an explicit target cannot bypass is claim state: a live local holder or a still-valid remote lease returns conflict `5` naming the holder; a remote lease conflict includes its remaining seconds. An expired remote lease is reconciled before admission, while a remote claim without a lease remains active for compatibility with older kc versions. `agent/blocked` with no unconsumed unblock request returns conflict `5` with `kc blocked-continue --issue <N>` as the suggestion; unreadable or closed returns `3 not_found`. A dead local holder (PID gone) is not a conflict — the run resumes the in-flight work. An empty ready queue stays the normal, silent, exit-0 case.
- **The daemon mutex covers queue polling only**: an explicitly targeted `kc run --issue <N>` coexists with a live daemon. A live remote lease still blocks the named Issue. Whole-daemon takeover interrupts all of its Issues and needs explicit authorization. Take over a single active verifier through the Console triage route.
- **First claims use an election.** Only the winner changes workflow labels. Other bidders leave `kc:claim-withdrawn` and skip the Issue. See run-once for the claim protocol.
- **FAST and DIRECT are explicit single-Issue choices.** Follow the run-once reference before passing `--fast-merge`, `--direct-pr` or setting a publication label. DIRECT requires a readable Issue with no PRD anchor. Keep PR disclosures and the applicable verification gates.
- **The `direct-pr` Issue label (direct tier that travels with the Issue)**: an explicitly marked Issue can carry DIRECT to an upgraded claimer — another machine, a batch pass, the daemon. The winner re-reads labels/body after claiming, resolves only that Issue, and freezes the tier for this execution round (including fallback/recovery); read failures fail closed. It changes neither queue eligibility, priority, nor claim ownership. It is **not** a workflow state label; a PRD-anchored Issue is refused before any build or PR, and FAST plus label is a usage error instead of a silent upgrade. Only the winner consumes it after confirming the current round's PR association, branch, marker and head **at the published head**; a historical same-head PR alone never counts. Failures preserve it; deletion/handoff failures report the PR URL and "cleanup pending". Recovery finishes that same handoff only: no rebuild, no duplicate PR, even if the label was already removed before a crash. Create the configurable name with `kc labels sync` (`[agent_runner.labels] direct_pr`). See run-once for decision/validation duties, upgraded-claimer requirements and the unsupported concurrent re-add window.
- **The `prd-auto-merge` Issue label (single-PRD authorization)**: this is a user-selected Backlog option, not an agent optimization. Never add it based on task urgency or an agent's confidence. It skips only the independent verifier; PRD delivery, Realistic Validation evidence and commands, review agents, post-PR supervision, queue verification commands, forbidden-path scan, PR checks and branch protection remain. `autopilot.enabled` and a running review pass are still required; global `safety.auto_merge` can stay false, and this label only authorizes the marked PRD. The explicit choice authorizes the queue to pass that PRD's `Human-Confirmed` hold, but it does not create human confirmation: after merge, do not tick PRD `Human-Confirmed`, change its acceptance banner, or append a PRD acceptance Change Log. `kc labels sync` creates the configurable label (`[agent_runner.labels] prd_auto_merge`). **The `auto-merge` Issue label (general per-Issue authorization)**: a user may apply it to any Issue, including one with no PRD; never add it based on an agent's confidence. With `autopilot.enabled = true`, it opts that Issue into the normal merge queue even while global `safety.auto_merge` is false. It does not bypass the configured verifier policy, repository verification commands, forbidden-path scan, PR checks, branch protection, or a PRD's `Human-Confirmed` hold. If a PRD exists and still has human sign-off items, the queue waits for the human. `kc labels sync` creates the configurable label (`[agent_runner.labels] auto_merge`); use `prd-auto-merge` only when the PRD-specific verifier and sign-off behavior is intended.
- **Publication-tier decisions**: use NORMAL for public constructors, cross-layer contracts, schema/migrations, security boundaries, unclear scope, or failed/stale/insufficient-fidelity evidence. FAST/DIRECT never authorize fabricated, weakened, or omitted necessary final-tree validation; read `${CODEBUDDY_SKILL_DIR}/references/run-once.md` for the decision protocol before setting a label or bypass flag. Existing explicit write authorization carries forward; there is no rationale parameter or extra approval round.
- **Issue without a PRD:** use `kc issue create --from-prompt "<需求>"` and follow the create-issue reference for ready state and `--require-validation`.
- **Backlog auto-advance and parallelism belong to the daemon.** Follow the daemon reference for live settings and precedence. Auto-advance does not authorize auto-merge.
- A user-owned `kedacode-operator` Skill with different content is preserved by default. `kc init --dry-run` reports the conflict. Only pass `--force` when the user explicitly requests replacing that file.
- **Packaged Skill upgrades**: when a native session starts, KedaCode checks the selected Agent's `kedacode-operator` directory and refreshes exact, unedited copies from prior releases. A customized managed file is preserved and blocks startup until reviewed. Preview a repair of just that directory with `kc skill repair-operator --skill-dir <absolute-path> --dry-run`; add `--force` only after the user explicitly asks to overwrite its managed files. Other Skill roots, remote Skills, and user-added files are not touched by this command.
- **Old-name packaged copy cleanup**: installing the packaged operator Skill — via `kc init` or the config-free `kc skill install` — also checks every install root for a leftover operator Skill published under the previous name. It removes one only when the directory holds nothing but the known packaged files and its `SKILL.md` matches a past packaged version byte for byte; a modified copy is kept and its path is reported so nothing is lost silently. `--force` (on either command) removes the old-name copy outright. Prefer `kc skill install` when the repository already has a `.kedacode.toml`: `kc init` stops at its first step when that config exists and only `--force` proceeds, rewriting the whole file.
- The PRD runner currently accepts Machine Contract v3, v4, and v5. Versions outside the supported set fail preflight before GitHub state writes. Updating the installed `prd` Skill is a separate action: `kc skill install` refreshes it without touching any repository config, and its `--force` (like any `--force`) is only for an explicit replace request — do not recommend blind `kc init --force`, because it rewrites the whole `.kedacode.toml`.
- Ready Issue priority comes from `priority/P0` through `priority/P3` labels. Selection order is P0, P1, P2, P3, then Issues without one of those labels; ties use ascending Issue number. Dry-run and execution share this ordering; the runner sorts only the GitHub-returned candidate window (currently at most 100 ready Issues per pass), not every ready Issue.

**Lifecycle reference:** For repository setup, Issue/PRD commands, one-shot runs, viewing and triaging agent output, registry-managed daemons, logs, and shutdown steps, read `docs/guides/agent-runner.md` in the KedaCode repository — it ships with that repository, not inside this Skill directory, so the path is not resolvable from an installed copy. In particular, use its daemon lifecycle section before starting persistent processes.

- Draft PR title/body generation defaults to deterministic publication (`generated_content.draft_pr.enabled = false`), with commit facts and tracked validation-report references. Set this target to `enabled = true` to opt into AI writing; this does not change review, validation, verifier, or merge gates. The body itself never establishes PASS. Existing explicit target settings are respected. AI generation also reads local repository Issue/PR templates; scope and fallbacks are in `${CODEBUDDY_SKILL_DIR}/references/create-issue.md`.
